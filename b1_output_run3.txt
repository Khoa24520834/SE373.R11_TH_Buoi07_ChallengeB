## Nguyên nhân khả dĩ

Tất cả trỏ về `refreshToken()` trong `session.ts:6-12`:

```ts
const row = await db.one("SELECT token ... AND token = $2 AND revoked = false", ...); // 1. kiểm tra
if (!row) throw new Error("invalid refresh token");
const next = crypto.randomUUID();
await db.none("INSERT INTO refresh_tokens (...)", ...);                              // 2. cấp token mới
await db.none("UPDATE refresh_tokens SET revoked = true WHERE token = $1", [oldToken]); // 3. thu hồi token cũ
```

Đây là mẫu **check-then-act không nguyên tử** (TOCTOU):

- 3 lệnh SQL chạy thành 3 câu lệnh riêng lẻ, **không bọc transaction** (`db.tx` có sẵn trong `db.ts` nhưng không được dùng) và **không khoá dòng** (`SELECT ... FOR UPDATE`).
- Với 2 request refresh song song dùng chung 1 token cũ: cả hai cùng đọc được `revoked = false` trước khi request nào kịp chạy `UPDATE` → cả hai đều `INSERT` token mới → user có **2 token đang active** → fail test #1 và #3.
- Với test #2: lệnh `SELECT` kiểm tra "token cũ đã bị thu hồi chưa" chạy **trước** lệnh `UPDATE` thu hồi của request rotation đang in-flight, nên token cũ vẫn được coi là hợp lệ → trả **200** thay vì 401.

Hai điểm phụ củng cố lỗi:
- Lệnh thu hồi `UPDATE ... WHERE token = $1` **thiếu điều kiện `AND user_id = $2`** và `AND revoked = false` → có thể thu hồi nhầm dòng của user khác nếu token trùng, và không chống chạy lại (non-idempotent).
- Không có ràng buộc DB nào (partial unique index `UNIQUE (user_id) WHERE revoked = false`) để chống 2 token active cùng lúc — logic chỉ dựa vào code ứng dụng.

## Kết luận

TTL **không phải** nguyên nhân của 3 lỗi này — tăng thời hạn token không làm thay đổi kết quả. Cả 3 lỗi đều thuộc nhóm *refresh-token rotation không nguyên tử*:

Trong `refreshToken()` (`session.ts`), 3 bước chạy tách biệt, không bọc transaction:
1. `SELECT token ... WHERE revoked = false` (kiểm tra)
2. `INSERT` token mới
3. `UPDATE ... SET revoked = true` (thu hồi token cũ)

Khi 2 request refresh chạy song song với cùng một token (đúng trường hợp mobile resume gọi nhiều request cùng lúc — comment trong `auth.ts` cũng nhắc tới điều này), cả hai đều đọc được token cũ còn hợp lệ trước khi bước 3 của request kia chạy → cả hai cùng cấp token mới (`got 2` token active), và token cũ vẫn được dùng lại được (`got 200` thay vì 401).

## Hướng sửa đề xuất (chưa thực hiện)

Vì `db.ts` đã có sẵn `db.tx`, có thể gom check + insert + revoke vào một transaction và thêm ràng buộc duy nhất (unique partial index trên `refresh_tokens(user_id) WHERE revoked = false`) để chặn race condition ở mức DB. Bạn có muốn tôi thực hiện không?
