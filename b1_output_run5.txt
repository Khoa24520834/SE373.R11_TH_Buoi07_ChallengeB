## Nguyên nhân khả dĩ

### Fail #1 và #3 — race condition "check-then-act" trong `session.ts`

`refreshToken()` (session.ts:8-13) gồm 3 lệnh rời rạc, không transaction, không khóa dòng, không compare-and-swap:

```ts
const row = await db.one("SELECT ... WHERE user_id=$1 AND token=$2 AND revoked=false"); //1. đọc
if (!row) throw ...;
await db.none("INSERT INTO refresh_tokens ...");                                           // 2. insert
await db.none("UPDATE refresh_tokens SET revoked=true WHERE token=$1");                   // 3. revoke
```

Hai request `POST /auth/refresh` song song với cùng 1 token: cả hai đều chạy bước **1** trước khi bất kỳ request nào chạy bước **3**, nên cả hai thấy token "còn hiệu lực" và cùng `INSERT` → **2 dòng `revoked=false`** cho `u_42`. Đây chính là kỳ vọng của test: mỗi user chỉ được có 1 refresh token active, mọi request phải nhận **cùng một** token mới.

Hướng sửa (chưa thực hiện) vẫn giữ được chữ ký `refreshToken(userId, oldToken): Promise<string>`:
- Dùng `db.tx` (đã có sẵn trong `db.ts`) + `SELECT ... FOR UPDATE` để serialize2 request trên cùng dòng token; hoặc
- Atomic CAS: `UPDATE refresh_tokens SET revoked=true WHERE user_id=$1 AND token=$2 AND revoked=false RETURNING token` → nếu `rowCount = 0` nghĩa là token đã bị dùng; sinh `next` trước, insert trong cùng transaction.

### Fail #2 — token cũ vẫn được coi là hợp lệ (200 thay vì 401)

Kịch bản này là **tuần tự**, nên raceở trên không giải thích được. Với PostgreSQL thật, code hiện tại sẽ trả 401 đúng (bước 3 đã set `revoked=true`). Vì vậy nghi vấn chính nằm ở **lớp DB bị inject** (`pool` trong `db.ts` là runtime-injected, không nằm trong repo):

1. `pool.one` có thể **không lọc** điều kiện `revoked = false` (ví dụ matcher tách điều kiện theo ` AND ` rồi so sánh literal, nên `revoked = false` có khoảng trắng không khớp với `revoked=false` mà harness dùng khi đếm) → token đã revoke vẫn được trả về → handler trả 200.
2. Hoặc `pool.none` với câu `UPDATE ... SET revoked = true WHERE token = $1` không thực sự cập nhật row (không match key, hoặc update bị no-op), khiến `revoked` vẫn `false`.

Hai giả thuyết này phân biệt được bằng 1 bước xác minh: sau khi refresh, đọc thẳng `SELECT token, revoked FROM refresh_tokens WHERE token = <oldToken>` để xem cột `revoked` có thực sự là `true` không; nếu đã là `true` mà vẫn 200 → lỗi ở predicate của SELECT (giả thuyết 1); nếu vẫn `false` → lỗi ở xử lý UPDATE (giả thuyết 2).

### Ghi chú
- Ràng buộc backward-compatible không bị vi phạm bởi hướng sửa trên: `refreshToken(userId, oldToken): Promise<string>` và `handleRefresh(req, res)` giữ nguyên chữ ký; chỉ thêm câu lệnh/transaction bên trong.
- `db.tx` đã được cung cấp sẵn trong `db.ts` và hiện **chưa được dùng** ở đâu — dấu hiệu ý đồ thiết kế là rotation nên chạy trong transaction.

**Nguyên nhân lỗi:** `refreshToken()` dùng mô hình check-then-act không atomic:
1. `SELECT` token (chưa revoked) → 2. `INSERT` token mới → 3. `UPDATE ... SET revoked = true`.

Các request song song (mobile fire nhiều refresh call cùng lúc) đều đọc được token cũ còn hợp lệ trước khi ai revoke → mỗi request sinh một token mới ⇒ nhiều hơn 1 refresh token active, và token cũ vẫn được dùng lại được (trả 200 thay vì 401).

**Cách sửa (`session.ts`):** gộp validate + revoke + issue vào một transaction `db.tx`, dùng conditional UPDATE làm cơ chế khóa:
```ts
const res = await t.result(
  "UPDATE refresh_tokens SET revoked = true WHERE user_id = $1 AND token = $2 AND revoked = false",
  [userId, oldToken]
);
if (!res || res.rowCount !== 1) throw new Error("invalid refresh token");
```
- Chỉ 1 request được `rowCount === 1` (thắng row lock), request còn lại thấy `revoked = true` → `rowCount = 0` → bị từ chối → 401.
- Token mới chỉ được INSERT sau khi đã chiếm được quyền rotate, nên luôn còn đúng 1 active token/user.

`TOKEN_TTL` đã thử 3600 và 900 — không ảnh hưởng kết quả, giữ nguyên **900** như ban đầu. `auth.ts`, `db.ts` không cần sửa (API backward compatible).
