## Nguyên nhân khả dĩ

Tất cả đều trỏ về `refreshToken()` trong `session.ts:6-13`:

```ts
const row = await db.one("SELECT ... AND revoked = false", [userId, oldToken]);   // 1. đọc
if (!row) throw new Error("invalid refresh token");
const next = crypto.randomUUID();
await db.none("INSERT INTO refresh_tokens (...) VALUES (...)", [...]);            // 2. insert token mới
await db.none("UPDATE refresh_tokens SET revoked = true WHERE token = $1", [oldToken]); // 3. revoke token cũ
return next;
```

1. **Không atomic — race TOCTOU ( gây fail #1 và #3).** Ba lệnh chạy rời rạc, **không có transaction, không có `SELECT ... FOR UPDATE`, không có `UPDATE ... WHERE revoked = false` có điều kiện**. Khi mobile bắn 2 request refresh song song (đúng như comment ở `auth.ts:5`), cả hai request đều pass bước 1 (thấy `revoked = false`) trước khi bước 3 của request kia chạy → cả hai cùng `INSERT` → user có **2 token active** → vi phạm invariant "một session active".

2. **Vòng đời rotate sai thứ tự → token cũ vẫn được dùng lại (fail #2).** Token mới được `INSERT` **trước khi** token cũ bị `revoked`, và việc revoke nằm ở lệnh riêng biệt (không cùng transaction). Trong khoảng thời gian đó, request retry dùng lại token cũ vẫn được `SELECT` thấy với `revoked = false` → `refreshToken` trả token mới → HTTP **200** thay vì 401. Tức là rotation hiện tại **không idempotent**: cùng một request có thể phát hành nhiều token.

3. **Thiếu mapping lỗi → 401 ở tầng HTTP.** `handleRefresh` (`auth.ts:4-9`) không có `try/catch`, không `res.status(401)`. Nên ngay cả khi `refreshToken` ném `"invalid refresh token"`, HTTP client cũng không bao giờ nhận được 401 mà là lỗi 500/unhandled rejection. Đây là lý do trực tiếp khiến kỳ vọng "401" trong test #2 không bao giờ thành hiện thực.
