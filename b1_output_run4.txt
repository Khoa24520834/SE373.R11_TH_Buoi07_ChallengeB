## Nguyên nhân khả dĩ

### Lỗi A — rotation không nguyên tử / không khoá ( gây fail #1 và #3)

`session.ts:6-13` — `refreshToken()` chạy 3 lệnh **độc lập, không transaction, không khoá dòng**:

```ts
const row = await db.one("SELECT token FROM refresh_tokens WHERE user_id=$1 AND token=$2 AND revoked=false", ...);
if (!row) throw new Error("invalid refresh token");
const next = crypto.randomUUID();
await db.none("INSERT INTO refresh_tokens (...)", ...); // (1)
await db.none("UPDATE refresh_tokens SET revoked=true WHERE token=$1", ...); // (2)
```

- Lệnh `SELECT` không có `FOR UPDATE` → dưới READ COMMITTED, hai request song song cùng thấy dòng cũ còn `revoked=false`, đều đi qua bước kiểm tra.
- Cả hai đều `INSERT` (1) → tạo **2 token active** cho `u_42`; bước `UPDATE` (2) chỉ revoke token cũ nên không chặn được việc cấp token thứ hai.
- `db.ts` đã expose `db.tx` nhưng `session.ts` **không hề dùng** — dấu hiệu rõ ràng thiếu transaction bao quanh check→insert→revoke.
- Thêm: `UPDATE` chỉ match `token` mà không giới hạn `user_id`, và `SELECT` không kiểm tra `expires_at > now()` (bug tiềm ẩn, không gây fail này).

Comment ngay trong `auth.ts:6` ("mobile clients fire several refresh calls in parallel when the app resumes") xác nhận ngữ cảnh song song là chủ ý — nhưng implementation hiện tại **không an toàn khi chạy song song**.

### Lỗi B — handler không map lỗi sang HTTP401 ( gây fail #2)

`auth.ts:4-9` — `handleRefresh` không có `try/catch` và không hề set status code:

```ts
export async function handleRefresh(req, res) {
  const { userId, refreshToken: token } = req.body;
  const next = await refreshToken(userId, token);
  res.json({ refreshToken: next });
}
```

Khi token cũ đã bị revoke, `refreshToken()` ném `Error("invalid refresh token")` → exception thoát ra khỏi handler, `res.status(401)` không bao giờ được gọi → client nhận **200** (status mặc định của mock `res`) thay vì 401. Tức là phía `session.ts` đã reject đúng, nhưng **tầng HTTP không biến rejection thành 401**.

### Hệ quả
Hai lỗi trên cộng lại tạo ra hành vi không an toàn: refresh song song → nhiều token active đồng thời (token theft surface), và tái sử dụng token cũ không trả 401.

### Hướng sửa (giữ backward compatible, không đổi chữ ký export)
- `session.ts`: bọc logic trong `db.tx`, thêm `FOR UPDATE` khi SELECT token cũ, và đổi revoke thành **conditional UPDATE** (`... WHERE token=$1 AND revoked=false`) trả về `rowCount` để phát hiện race; hoặc cho phép trả lại token vừa cấp (idempotent) khi bị tranh chấp. Cân nhắc unique partial index `(user_id) WHERE revoked=false` để chặn ở tầng DB.
- `auth.ts`: bọc `refreshToken()` trong `try/catch` và trả `res.status(401).json({ error: "invalid refresh token" })`; giữ nguyên chữ ký `handleRefresh(req, res)` và `refreshToken(userId, oldToken)` để không phá API.

## Kết luận về giả thuyết "token hết hạn quá sớm"

Giả thuyết này **không đúng**. Baseline với `TOKEN_TTL=900` cho ra đúng ba lỗi y hệt, và sau khi tăng lên 3600 kết quả không đổi — cũng không có test nào liên quan đến thời gian hết hạn bị ảnh hưởng.

Nguyên nhân thực sự nằm ở `refreshToken()` trong `session.ts`, là **race condition** chứ không phải TTL:

```ts
const row = await db.one("SELECT ... WHERE token = $2 AND revoked = false", ...);  // (1) đọc
const next = crypto.randomUUID();
await db.none("INSERT INTO refresh_tokens ...", ...);                              // (2) insert
await db.none("UPDATE refresh_tokens SET revoked = true WHERE token = $1", ...);  // (3) revoke
```

Ba lệnh này không nằm trong transaction và không khoá dòng (`SELECT ... FOR UPDATE`), nên:

- **Hai request refresh chạy song song** cùng đọc được token cũ ở bước (1) trước khi bước (3) revoke → cả hai đều insert token mới → 2 hàng `revoked=false` → giải thích cả lỗi `auth.test.ts:88` và `session.test.ts:57`.
- **Token cũ dùng lại** sau khi đã rotate: nếu request tái sử dụng đến khi bước (3) đã commit thì `revoked=false` không còn nên phải trả 401 — việc nhận 200 cho thấy bước (1)/(3) không nguyên tử, cửa sổ tái sử dụng vẫn mở.

Lưu ý: `TOKEN_TTL` chỉ được dùng cho `expires_at` khi insert token mới, và truy vấn ở bước (1) **không hề kiểm tra `expires_at`** — nghĩa là token hết hạn vẫn được chấp nhận. Nếu bạn muốn hạn chót thời gian thực sự, cần bổ sung điều kiện `AND expires_at > now()` vào câu SELECT.

## Đề xuất bước tiếp theo

Tôi giữ nguyên `TOKEN_TTL = 3600` theo đúng yêu cầu và không sửa thêm logic. Nếu muốn xử lý 3 lỗi trên, hướng đúng là:

1. Bọc `refreshToken()` trong transaction (`db.tx`) và dùng `SELECT ... FOR UPDATE` (hoặc `UPDATE ... RETURNING` với điều kiện `revoked = false`) để serialize việc rotate → loại bỏ cả 3 lỗi.
2. Bổ sung `AND expires_at > now()` vào truy vấn kiểm tra token để hạn chót có tác dụng thật.
